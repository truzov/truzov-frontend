# Product management investigation — 2026-10-28

This is the read-only answer to UI fix task 6; no product-management code was changed for this investigation.

- The real admin/seller application is ADMIN/Main_File/Sellzy_Dashboard. Both roles use /products, /products/add and /products/edit/[id], sharing components/panel/products.tsx. Vendor product endpoints are /api/v1/vendor/products (GET/POST) and /{id} (GET/PUT/DELETE); storefront workspace aliases also exist under /vendor. Admin creation/edit uses /api/v1/admin/products (POST) and /{id} (GET/PUT), with publish/featured/merchandising switches in admin ops. Deletion is supported by the vendor backend; the shared list currently exposes edit/unpublish controls rather than a complete admin delete workflow.
- The shared form accepts name, brand, category, weight/size, selling price, MRP, stock, tags, description, up to eight uploaded images, and publication. Admin chooses an approved active owner for new products and controls Featured and Auto/force-on/force-off bestseller/new modes. Existing benefits/ingredients/certifications arrays survive edit mapping, but do not have full dedicated form editors. Slug and extra arrays are accepted by the backend contract.
- ImageUpload uses authenticated POST /api/v1/media with kind=public. The server checks JPEG/PNG/WEBP content, enforces 5 MB and random storage IDs, and returns Cloudinary HTTPS URLs. URLs are then persisted with the product; first image is the cover. Product images are intentionally public; support attachments introduced in this change use private authenticated storage separately.
- VendorContext derives the vendor from the verified JWT subject, and all vendor reads/writes match that owner. Clients cannot submit a vendorId to vendor APIs. Admin APIs require ADMIN plus the live admin audit authorization. The owner of an existing product cannot be transferred through edit; approved/active owner validation applies on admin create. A vendor cannot edit another vendor's product.
- Lab reports follow a separate submission/lab/admin approval workflow, not a seller assertion in the product form. DB category rows/FKs and final merchandising flags are reused.
- Gaps relative to a mature marketplace: dedicated editing for benefits/ingredients/certifications, a clearly surfaced complete delete/archive flow, richer variant editing, and attaching/reporting lab workflow progress from the product editor. These are findings only, not additional builds requested by task 6.

Seller application recommendation (task 14): keep initial enquiries public to avoid sign-up friction, but never grant access from an unverified form. Public /apply in the seller panel and the existing storefront /support/seller persist the same enquiry record. Staff contact applicants, then the existing verified account/KYC/approval flow determines access. Advantages: easy initial contact, existing ownership/approval security retained. Trade-off: review and account activation are separate, with manual staff follow-up; automated invitations are not implemented or falsely implied.

Assumptions: retain neutral keyboard focus; use lowercase letters rather than typographic small caps; retain existing filter choices pending Rohit's confirmation; an enquiry does not create an account or assign VENDOR privileges.
