## Sign-in investigation (2026-09-27)

- Local PostgreSQL container is healthy; the Spring backend is listening on `localhost:8080`. `GET /actuator/health` and `GET /api/v1/products` return 200.
- `POST /api/v1/auth/account/exists` with the seeded `arya@example.com` returns 200 and `{"data":{"exists":true}}`. The response permits origin `http://localhost:3000`; API origin and envelope handling match the frontend configuration.
- `POST /api/v1/auth/login` with `arya@example.com` and an incorrect password returns 401 `UNAUTHORIZED` / `Invalid credentials.` The seeded `arya@example.com` and `owner@truzov.com` have 57-character placeholder password hashes. BCrypt hashes generated by this app have 60 characters. Both seeded accounts also lack email and phone verification timestamps, so password login cannot be used for them even if the supplied password were known.
- The backend `dev` profile configures mock OTP with a fixed local code; its mock dispatcher explicitly sends no email/SMS by default. The active process profile was not confirmed here. OTP send/verify was left untested because it creates and consumes database records, outside this read-only QA check. If the active backend uses the `dev` profile, a user waiting for a delivered code will receive nothing by design and must use the configured local mock code. If it uses `live` without a delivery provider, `/auth/otp/send` returns 503 `OTP_DELIVERY_UNAVAILABLE`.
- The frontend was not listening on port 3000 during this investigation. Browser reproduction of the full login modal and guest-cart merge is therefore pending a running frontend and an explicitly scoped test account.
- Static check: `app/providers.tsx` mounts `useGuestCartMerge` and the guest bag persists in `localStorage`. Existing browser coverage checks guest add-to-cart, but does not exercise a real local sign-in and merge. No independent cart defect was reproduced.
